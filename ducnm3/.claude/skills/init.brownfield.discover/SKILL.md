# Init Brownfield — Discover

In a brownfield repo, the code is the spec. Nothing else in this workflow may invent decisions — every later step cites evidence captured here.

## Iron Law — Evidence Before Proposals

No ADR, no CI change, no doc edit happens until `.vibe/research/brownfield-init.md` records what is **already present** in the repo. If a fact isn't written there, downstream steps must re-read the file — they do not guess.

## Tool Discipline

A real brownfield repo can have 10k+ files. View-file-one-by-one will exhaust the context window before any useful output. Follow this order strictly:

1. **Manifests first** (always cheap, always informative): `package.json`, `pnpm-workspace.yaml`, `composer.json`, `pyproject.toml` / `requirements.txt`, `go.mod`, `Cargo.toml`, `Gemfile`, `pom.xml`, `build.gradle`. Read in full.
2. **Root config files**: `Dockerfile`, `docker-compose.yml` / `compose.yaml`, `.env.example`, `.editorconfig`, `.prettierrc*`, `.eslintrc*` / `eslint.config.*`, `tsconfig.json`, `.github/`, `.gitlab-ci.yml`, `Jenkinsfile`, `README.md`, `CONTRIBUTING.md`.
3. **Tree listing only** for `src/`, `app/`, `modules/`, `packages/`, `docs/` — use glob or directory listing, do not open individual source files unless a manifest signal requires disambiguation (e.g. conflicting DB drivers).
4. **Grep, don't read**, for signal hunting: env var usage (`process.env.`, `os.environ[`, `getenv(`), connection strings, auth library imports. One grep per signal; capture 2–3 example lines, not whole files.

**Context budget**: if cumulative file reads exceed ~30 files or ~200 KB of source, stop and summarize — downstream steps need decisive evidence, not exhaustive evidence.

**Never**: open every file under `src/`; read `node_modules/`, `vendor/`, `.git/`, lockfiles beyond version extraction, generated folders (`dist/`, `build/`, `.next/`).

## Scope — what to capture

Seven evidence groups plus two meta-sections. Every group uses the exact heading listed in the schema below — downstream steps parse by heading, so do not rename.

1. **Stack & frameworks** — from manifests. Exact versions. Runtime + primary framework + ORM/HTTP/UI libs.
2. **Runtime & dependencies** — Docker / compose presence; external services referenced (DB, cache, queue, 3rd-party APIs). Include versions when pinned, mark `unpinned` otherwise.
3. **Quality scaffolding** — lint, format, commit hooks, test runner, coverage. Record **presence vs absence**, not quality judgment.
4. **CI/CD** — one row per pipeline file: path · trigger events · stages visible.
5. **Docs** — list `README.md`, `CONTRIBUTING.md`, `docs/` tree top level, `docs/adrs/` existence.
6. **Conventions in use** — folder layout, naming patterns visible in the top 2 levels of `src/` (or equivalent).
7. **Gaps** — things expected but missing. Phrase as fact: "no CONTRIBUTING.md", "no CI", "tests directory empty". Absence is evidence.

Two meta-sections: **8. Uncertainty / conflicts** (only when signals conflict) and **9. Proposed next steps** (one row per downstream phase).

## Expected artifact — `.vibe/research/brownfield-init.md`

Write the file with this exact structure. Downstream steps parse by heading number and title.

```markdown
# Brownfield Init — Discover

> Generated by `init.brownfield.discover` on <ISO date>. Evidence only; no proposals live here except §9.

## 1. Stack & frameworks
- Runtime: <name> <version> (source: <file>)
- Primary framework: <name> <version> (source: <file>)
- Key libraries: <list with versions>

## 2. Runtime & dependencies
- Containers: <Dockerfile? compose? none>
- External services referenced in code: <Postgres | Redis | S3 | ...>
- Pinned versions: <service → version> · Unpinned: <list>

## 3. Quality scaffolding
- Lint: <tool + config file | absent>
- Format: <tool + config file | absent>
- Commit hooks: <tool | absent>
- Test runner: <tool + sample test path | absent>
- Coverage: <threshold + reporter | absent>

## 4. CI/CD
| File | Triggers | Stages observed |
| --- | --- | --- |
| .github/workflows/ci.yml | push, pull_request | lint, test |

## 5. Docs
- README.md: <present + section list | absent | stale>
- CONTRIBUTING.md: <present | absent>
- docs/ tree: <top-level entries>
- docs/adrs/: <count | absent>

## 6. Conventions in use
- Folder layout: <observed pattern>
- Naming: <kebab | snake | camel | mixed>

## 7. Gaps (absence as evidence)
- <bullet per missing item, phrased as fact>

## 8. Uncertainty / conflicts
- <each row: signal A vs signal B, where each was seen, how downstream should interpret>
  Example: "Both `pg` and `mongoose` in package.json; `pg` used in src/db/, `mongoose` only in scripts/legacy-import.ts → treat Postgres as primary, Mongo as legacy."

## 9. Proposed next steps
- Architecture (step 2): <one-line reason to run | SKIP because init.enabled_phases excludes it>
- Conventions (step 3): ...
- Environment (step 4): ...
- Pipeline (step 5): ...
- Documentation (step 6): ...
```

**Schema rules:**
- Section numbers 1–9 and exact headings are part of the contract. Do not renumber.
- Cite evidence as `<file>` or `<file>:<line>` — downstream steps may re-open the cited location.
- If a section has no findings, write `- (none observed)` — never omit the heading.

## §9 — proposed next steps rules

Section 9 is consumed by every other step to decide run vs skip. Write one row per downstream phase. For each:

- If `devkit.workflow-profile.json → init.enabled_phases` excludes a phase, write `SKIP (disabled by profile)`. Do not guess — only mark SKIP when profile explicitly disables.
- If the phase is enabled but the repo already satisfies it completely, write `RUN (verify only — no gaps found)`.
- Otherwise write a one-line reason: what the main gap is (e.g. "no ADRs, 5+ decisions visible", "no test runner", "CI missing test stage").

## Implementation Steps

1. **Read manifests** (section 1). Record runtime + framework + 5–10 top deps with versions.
2. **Inventory root configs** (sections 2, 3, 4, 5). One pass over known filenames — do not descend into source yet.
3. **Grep for signals** (sections 2, 6): env var usage, connection strings, folder structure. Keep 2–3 evidence lines per signal.
4. **List gaps** (section 7): everything expected but missing, phrased as fact with no proposal.
5. **Record uncertainty** (section 8): only when signals conflict — do not invent uncertainty.
6. **Write §9** using the rules above. Respect `init.enabled_phases`.

## Rerun behavior

If `.vibe/research/brownfield-init.md` already exists:

1. **Read the existing file first** to understand prior findings.
2. **Compare against current repo state** — note what changed (new deps, new services, CI changes).
3. **Overwrite** with current state and append a `## Changelog` section at the bottom listing deltas vs previous run. The changelog lets downstream steps detect drift.
4. **Do not overwrite if the previous file was hand-edited by a human** (detectable by sections outside the schema, rich commentary). Save as `brownfield-init.new.md` and flag for human reconciliation.

## Monorepo handling

If root manifests signal a monorepo (`workspaces` in `package.json`, `pnpm-workspace.yaml`, Nx / Turborepo config, Cargo `workspace`, Go multi-module):

- §1 captures the **root** stack only. Add a subsection `### 1a. Workspaces` listing each package with its own runtime + primary framework (one line each). Do not recurse into per-package deep dependency trees here.
- §3, §4 stay root-level (shared lint / CI).
- §2 aggregates: if any package references Postgres, record Postgres once at root with the list of packages using it.
- §6: per-workspace naming conventions only if they differ from root.

Downstream steps decide whether they operate root-wide or per-package.

## Forbidden

- Writing production code, ADRs, CI, or docs in this step. Pure read + note.
- Skipping missing items — absence is evidence downstream relies on.
- Opening source files speculatively. If a signal needs confirmation, grep first; open only the specific matching line range.
- Guessing versions. If unpinned, write `unpinned` — do not infer from lockfiles beyond the exact version string of the direct dep.
- Editorializing in §1–§8. Opinion only belongs in §9.

## Acceptance criteria

Confirm all of the below before approving this step:

1. `.vibe/research/brownfield-init.md` exists.
2. All 9 section headings are present (empty sections written as `- (none observed)`).
3. Every claim in §1–§6 cites a file path (at minimum).
4. §9 has one row per downstream phase with explicit RUN / SKIP / RUN (verify only).
5. Context budget stayed reasonable (no exhaustive source dumps).
